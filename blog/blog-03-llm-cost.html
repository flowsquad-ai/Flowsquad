Why Is Your LLM Bill So High?

The problem starts with a well-intentioned shortcut. When developers first integrate an LLM into their workflow — asking it to explain code, generate tests, or answer architecture questions — the simplest implementation sends as much context as possible. If the question is about a payment module, send the whole payments folder. If it's about an API, send the entire API layer. If you're not sure what's relevant, send everything.

This approach — sometimes called "prompt stuffing" or naive context injection — produces decent results but at catastrophic token costs. Here's the math:

  • Average mid-sized codebase: 500,000 lines of code
  • Tokenisation ratio: approximately 1 token per 4 characters ≈ 3.75 million tokens to represent the full codebase
  • GPT-4 Turbo pricing (input): $0.01 per 1,000 tokens
  • Full codebase injection per query: $37.50 per request
  • If your team runs 500 AI queries per day (a conservative estimate for a 20-person engineering team): $562,500/day

Obviously most teams don't send the entire codebase, but even sending a relevant subsystem — say, 150,000 tokens — at 500 queries/day produces a monthly bill of approximately $22,500. This is how teams end up with $12,000–$30,000/month LLM bills within weeks of enabling AI features.

The root cause: Token cost scales linearly with context size. Sending 10x more context than necessary means paying 10x the cost — and getting no better answers, because most of that context is irrelevant noise.

What Is the Difference Between Vector Search and Raw Prompt Injection?

Vector search is the production-grade solution to context management. Instead of deciding "what code is relevant to this question?" at query time by sending everything, you pre-index your codebase into a vector database, then retrieve only the semantically relevant chunks when a query arrives.

The process works in two phases:

Phase 1 — Indexing (runs once, or on code changes)

  1. Your codebase is chunked into logical units (functions, classes, modules)
  2. Each chunk is passed through an embedding model (e.g., text-embedding-3-small or a local Ollama embedding model)
  3. The resulting vector is stored in the VectorDB alongside the original code chunk
  4. Index update time for a 500k-line codebase: approximately 15–25 minutes on initial index, then incremental updates per commit

Phase 2 — Query (runs on every request)

  1. The user's question is embedded using the same model
  2. A cosine similarity search retrieves the top-k most relevant code chunks (typically 5–15 chunks)
  3. Only those chunks — plus the question — are sent to the LLM
  4. Typical context window per query: 2,000–5,000 tokens vs. 50,000–200,000 in naive approaches

The quality of answers is equal to or better than naive injection for most queries, because the irrelevant context in naive approaches actually degrades LLM focus. A model given exactly what it needs performs better than one buried in noise.

How Does FlowSquad's VectorDB Layer Work? (ChromaDB + Pinecone)

FlowSquad's VectorDB integration supports two backends: ChromaDB for on-premise and air-gapped deployments, and Pinecone for cloud deployments that benefit from managed vector infrastructure.

# FlowSquad vectordb configuration (config.yaml)
vectordb:
  provider: chromadb          # or "pinecone"
  chromadb:
    host: localhost
    port: 8000
    collection_prefix: "flowsquad_"
    embedding_model: "all-MiniLM-L6-v2"  # local model, zero egress cost
  pinecone:
    api_key: "${PINECONE_API_KEY}"
    environment: "us-east-1-aws"
    index_name: "flowsquad-prod"
    dimension: 1536             # matches OpenAI text-embedding-3-small
  indexing:
    chunk_size: 512             # tokens per chunk
    chunk_overlap: 64           # overlap for context continuity
    top_k_retrieval: 10         # chunks retrieved per query
    reindex_on_push: true       # auto-reindex on git push

When ChromaDB is used with a local embedding model (such as all-MiniLM-L6-v2), the embedding step itself costs zero tokens — it runs on your infrastructure. This means indexing a 500k-line codebase has no API cost at all. Only the final LLM completion call — with its ~4,000-token context — is billed.

Frequently Asked Questions

How does FlowSquad's LLM cost tracker work?

The LLM cost tracker intercepts every API call made through FlowSquad's LLM layer and records the model used, token counts (input and output), user identity, feature/function that triggered the call, and the resulting cost based on current provider pricing. Data is aggregated in real-time and available via the FlowSquad admin dashboard with daily, weekly, and monthly views, filterable by user, team, project, or LLM provider.

Does the VectorDB need to be re-indexed every time code changes?

FlowSquad supports incremental indexing — only the files that changed in a commit are re-chunked and re-embedded. For a typical PR (10–50 files changed), incremental re-indexing takes 30–90 seconds. Full re-indexing (triggered manually or on a schedule) is recommended after large refactors or dependency upgrades and takes 15–30 minutes for a 500k-line codebase.

Can I switch between ChromaDB and Pinecone without re-indexing?

FlowSquad supports export/import of vector indexes between backends. You can export your ChromaDB index to a portable format and import it into Pinecone (or vice versa) without re-running the embedding step. This is useful for teams migrating from on-premise to cloud deployment. Note that if the embedding model changes between backends, a full re-index is required.

What embedding models does FlowSquad support?

For cloud deployments: OpenAI text-embedding-3-small (recommended for cost/quality balance), text-embedding-3-large (higher quality, higher cost), and Amazon Titan Embeddings. For local/on-premise: all-MiniLM-L6-v2, nomic-embed-text via Ollama, and any Ollama-compatible embedding model. The embedding model is configured once per FlowSquad project and cannot be changed without re-indexing.

Does FlowSquad support routing queries to different LLMs based on complexity?

Yes. FlowSquad's Multi-LLM routing allows you to define routing rules in the platform configuration. Rules can be based on feature type (e.g., always use GPT-4 for HLD generation), query complexity score (estimated token count of the expected output), user role (analysts get GPT-3.5, admins get GPT-4), or explicit user selection. All routing decisions are logged for cost attribution purposes.
