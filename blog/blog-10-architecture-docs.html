Why Do Static Docs Become Stale Immediately?

The incentive structure of architecture documentation is fundamentally broken. Writing docs is a large, upfront, unrewarded investment. The person best qualified to write them — the architect or tech lead who built the system — has the least free time. And the reward for writing good docs comes to future team members, not to the person who wrote them.

The result is predictable: docs get written once, at the point of maximum motivation (usually post-project retrospective or onboarding a new hire), and then progressively diverge from reality as the codebase evolves. The divergence compounds:

  • After 3 months: component names and module paths in the docs no longer match the codebase
  • After 6 months: architectural decisions described in the docs have been superseded by newer decisions that were never documented
  • After 12 months: the docs describe the system that was originally built, which may share only a passing resemblance to the system that currently runs in production

A study of 200 enterprise software teams found that 73% of developers report that architecture documentation is rarely or never accurate relative to the current implementation. Despite this, teams continue to invest in documentation sprints, ADR (Architecture Decision Record) processes, and Confluence hierarchies that are out of date before they're published.

The root problem: Docs are written about code. Code changes faster than docs. The only way to solve this is to generate docs from code — not the other way around.

How Does FlowSquad's Design Generation Work? (2-Step Flow)

FlowSquad's HLD and LLD generation follows a two-step flow that mirrors how a senior architect would actually document a system — first understanding the big picture, then drilling into component-level detail.

Step 1 — Codebase Analysis and Context Building

FlowSquad uses its VectorDB index to perform a structural analysis of the codebase:

  • Entry point detection: identifies API routes, CLI entry points, message queue consumers, and event handlers that define the system's external interfaces
  • Module dependency graph: maps the import/dependency relationships between modules to identify layers and components
  • Data model extraction: identifies database models, schemas, and ORM definitions to understand the data layer
  • External integration detection: identifies calls to external APIs, cloud services, and third-party libraries that the system depends on
  • Technology stack identification: detects frameworks, databases, message brokers, and deployment indicators from configuration files and dependency manifests

Step 2 — Document Generation

Based on the structural analysis, FlowSquad generates the design document via the configured LLM with the analysis as context. The generation is grounded in the actual codebase — not invented architecture that may not reflect reality. For large codebases, the generation uses multiple LLM calls (one per major component or layer) to stay within context window limits while maintaining coherence across the document.

What Is the Difference Between HLD and LLD in FlowSquad?

DimensionHLD (High-Level Design)LLD (Low-Level Design)
AudienceEngineering VPs, architects, onboarding developers, non-technical stakeholdersTech leads, senior developers working in specific components
ScopeEntire system or serviceIndividual component, module, or feature
ContentSystem purpose, major components, data flows, external integrations, tech stackClass/module structure, API contracts, database schemas, algorithm descriptions, sequence diagrams
Generation time3–8 minutes1–3 minutes per component
Regeneration triggerMajor architectural changes, quarterly refreshOn PR review for affected components
Export formatsConfluence page, Markdown, PDFConfluence page, Markdown, inline Jira story attachment

HLD and LLD generation can be triggered independently. Teams typically generate the HLD first to establish the architectural context, then generate LLDs for specific components on-demand as they're being developed or reviewed.

How Do You Export Designs Directly to Confluence?

FlowSquad's Confluence integration provides a one-click export from the generated design document to a new or existing Confluence page. The export:

  • Creates the page in the specified Confluence space and parent page
  • Formats the document using Confluence's native storage format (not raw HTML) — preserving heading levels, code blocks, tables, and list formatting
  • Adds metadata labels: flowsquad-generated, hld or lld, and the project name
  • Includes a generation metadata section at the bottom: generated date, FlowSquad version, codebase commit hash, and a "regenerate" link back to FlowSquad
  • For HLDs, optionally generates a mermaid diagram of the system architecture as a code block (rendered natively in Confluence)
Keeping docs current: FlowSquad's GitHub integration can trigger LLD regeneration automatically when a PR is merged that significantly modifies a documented component. The regenerated LLD is pushed as a Confluence page update, keeping the documentation current without manual intervention.

Frequently Asked Questions

How accurate is the generated HLD when the codebase has significant undocumented complexity?

FlowSquad's HLD generation is grounded in what's actually in the codebase — it doesn't invent architecture that isn't there. For codebases with poor internal documentation (minimal docstrings, no inline comments), the generated HLD will accurately reflect the structural relationships between modules but may describe component purposes in generic terms where intent is unclear from code alone. Teams can improve HLD quality by adding minimal module-level docstrings or by providing a brief (1–3 sentence) description of each major component in the FlowSquad project configuration.

Can FlowSquad generate design docs for new features before they're built?

Yes. FlowSquad's design generation supports a "forward design" mode where you provide a requirement (from the refinement workflow) and FlowSquad generates a proposed LLD for how the feature should be implemented, given the existing codebase architecture. The forward design uses AskProduct to find the most relevant existing patterns and proposes an implementation approach consistent with your existing conventions. This is particularly useful for architecture review — you review and approve the LLD before development begins.

How does Confluence export handle versioning — does it overwrite previous docs?

By default, FlowSquad creates a new Confluence page version on each export — Confluence's native versioning preserves all previous versions, and you can compare any two versions side by side. FlowSquad tags each version with the git commit hash at generation time, making it easy to correlate doc versions with codebase states. You can optionally configure FlowSquad to create a new page (rather than a new version) on each generation, for teams that prefer a complete archive of design snapshots.

What LLM is used for design generation — and does quality differ between models?

FlowSquad uses the LLM configured for your project (OpenAI GPT-4 Turbo, Claude 3.5 Sonnet, or a local Ollama model). GPT-4 Turbo and Claude 3.5 Sonnet produce the highest-quality HLDs — particularly for prose sections and architectural insight. Local models (Llama 3.1 70B) produce good structural output but may require more post-generation editing for the narrative sections. We recommend using a cloud model for HLD generation even in hybrid deployments where routine queries use local models.

Can generated LLDs include sequence diagrams automatically?

Yes. When include_sequence_diagrams: true is configured, FlowSquad generates Mermaid sequence diagrams for the key flows in each LLD component. The diagrams are inferred from the code's call graph — FlowSquad traces function call sequences from entry points through the component's public API to understand the interaction order. Sequence diagrams are embedded as Mermaid code blocks in Confluence (rendered natively by the Mermaid plugin) or as Markdown code blocks for other export targets. For complex components, FlowSquad generates 3–5 sequence diagrams covering the most common flows.
